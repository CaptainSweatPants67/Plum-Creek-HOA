## Member forms

Open **My information & properties**. Contact information now separates first name, last name, phone, mailing street, unit, city, state/province, ZIP/postal code and country. Previously saved combined names and addresses appear as references; the system does not guess how to split them. Saving derives the compatible display name and mailing address and updates only the contact explicitly linked through a prior property approval.

The optional consent checkbox uses the exact statement: **I consent to emailed notices in lieu of mailed notices to my property. I agree to keep my email address up to date.** It starts unchecked. Saving records the choice against the current confirmed account, server timestamp, confirmed email and statement version. Unchecking and saving withdraws consent. Repeated saves without a choice change do not fabricate consent history. Authorized staff see consent and its date in property verification reviews. The preference applies to HOA notices and does not suppress account-security messages. Recording consent does not itself send a notice or implement a bulk notice delivery system.

The collapsible **Login email** form requests a new address and a matching confirmation entry through Supabase Auth. The live `double_confirm_changes=true` setting was verified without changing SMTP settings. Users confirm links at both the current and new addresses before the login address changes. Pending changes are shown separately. The existing `/portal/` redirect is allowed; password recovery retains `/portal/reset-password/`. No actual email change or email was initiated for verification.

Under **Household members & trusts**, open an active property request to record up to ten additional people, including a spouse, joint owner or other household member. Each has first/last names and optional email/phone. A trust-owned home requires the trust name plus the decision maker's first/last names, with optional email/phone. Staff can read submitted details under **Households & trusts**. These are descriptions for independent review: they do not create Auth accounts, verify ownership or grant roles. Each person who needs access registers and obtains their own ownership approval. Existing rental PDF and current lease-date requirements continue to apply.

## Meetings and events

Serving Directors, Officers and administrators with MFA can edit the collapsible **Meetings & events** section in HOA administration. The Officer & Director tools have the same editor under a task button. Enter a meeting or community event, date, optional Central-time start/end times, location, address and details. Choose **Public website and member calendar** or **Members only**. Leave publish unchecked for a leadership-only draft. Published public entries appear on `/events/`; both kinds of published entries appear in the member library calendar. Reads recheck the member rental gate. The public table policies and anonymous RPC cannot reveal drafts or member-only entries.

Cancel an event to retain a cancellation notice, or unpublish it to withdraw it. The editor preserves past dates with filters for upcoming, drafts, past and all entries. The reviewed October 9, 2026 Annual Meeting was copied from `Info/Events.txt` into the database rather than removed. Upcoming lists use the Central-time date. Calendars refresh on page load or window focus; no email is sent by publishing.

## Service password safe

Open **Officer & Director tools → Service contacts → a contact card → Password safe & account details**. Contracts remain on the same card. The safe can store labeled service URLs, usernames, passwords, account and routing numbers, and private credential notes. Keep secrets here rather than the ordinary notes field.

Credential access defaults to **administrators with MFA only**, narrower than ordinary service-contact access. The server rechecks the authoritative admin role, confirmed account, signed MFA claims and an actual active MFA session on each operation. Enter a fresh authenticator code to unlock for five minutes. The signed authenticator verification must be within 60 seconds at unlock. List responses contain only record IDs, labels and update dates. Explicit **Reveal credential** fetches values; revealed details and existing-record edit forms hide after one minute, on window blur, when the tab becomes hidden or the safe is collapsed. Closing a contact clears its component; signing out clears sensitive state. Password/account edit fields are masked by default. **Lock password safe** closes the server unlock immediately. Role or session revocation blocks access immediately even during an unlock.

All credential values are serialized into an encrypted Supabase Vault secret, not plaintext contact or public table fields. Metadata and five-minute unlocks are in private tables, with no direct client grants. Save, reveal and remove are audited using IDs and action names only; credential values are excluded. Browser code does not put credential values into local/session storage. Supabase's encrypted database storage still permits privileged database administrators to decrypt records; this is not a zero-knowledge password manager. Removing a credential explicitly removes both its metadata and encrypted Vault record. No automatic deletion is scheduled.

Vault records consume database storage, not the hosted-file allowance. Each credential payload is limited to 16,000 bytes; 100 maximum-size payloads total at most 1.6 MB of plaintext before encryption, indexes and database overhead. Existing 2 MB contract, 1 MB publication, 2 MB rental-PDF and shared 800 MB file reservation limits remain in place. Monitor total database/storage/egress usage in Supabase as records grow.
